# GitHub 自动发布

普通分支推送和 PR 自动运行检查；推送 `v主版本.次版本.修订版本` 标签后，
`Publish release` 工作流复用现有 Windows / Python 3.12 检查，通过后自动创建正式 Release。
例如 `v0.1.0`、`v0.1.1` 和 `v0.2.0`。当前不发布开发快照或带后缀的预发布标签。

## 发布操作

首次使用时将本次发布流程变更提交并推送到 GitHub，确认仓库 Actions 已启用。
工作流使用内置 `GITHUB_TOKEN`，发布任务显式申请 `contents: write`，无需另设个人令牌。
若组织策略限制写权限，需要仓库管理员允许此工作流写入仓库内容。

在需要发布的提交上执行，版本号每次换成尚未使用的新版本：

```powershell
git push origin HEAD
git tag -a v0.1.0 -m "发布 v0.1.0"
git push origin v0.1.0
```

在 GitHub 的 Actions 页面查看 `Publish release`，完成后到
[Releases](https://github.com/PleaseBelieveLight/dafeiyu-companion/releases) 下载。
发布以标签对应的提交为准，可以从选定分支发布；推标签前请核对当前提交。
仅推送普通提交会运行检查，需要发布时才推送版本标签。

## 产物与检查

- `dafeiyu-companion-v0.1.0.zip`：解压后的顶层为 `dafeiyu-companion/`。
  包含 Git 跟踪且在分发白名单内的源码、安装工具、插件、补丁、`content/`、文档与许可证。
- `SHA256SUMS.txt`：ZIP 的 SHA256 校验值。
- Release 正文：源码提交、安装与升级说明、验证范围，以及自上一可达较低版本标签以来的非合并提交记录。
  没有较低版本标签时包含当前提交之前的完整非合并提交记录。

发布会拒绝无效版本标签、标签与 HEAD 不一致、已修改的跟踪文件、非白名单跟踪文件、
符号链接或目录联接，以及现有分发检查识别出的凭证或运行文件。
未跟踪文件不进入 ZIP，`AGENTS.md`、本机账号配置、依赖、缓存和运行数据不进入发布包。
源码分发检查不是通用密钥扫描器，新增配置仍需按项目要求使用空凭证模板。

工作流先完成源码测试、分发检查和语法检查，再打包上传到草稿，最后公开发布。
这些检查不包含真实 QQ 登录、付费模型调用和完整部署验收。
发布不修改本机运行目录；使用者升级前先备份，保留原运行目录、账号配置和持久化数据，
更新源码后按[脚本说明](../scripts/README.md)运行部署更新。

在 PowerShell 核对下载文件：

```powershell
Get-FileHash .\dafeiyu-companion-v0.1.0.zip -Algorithm SHA256
Get-Content .\SHA256SUMS.txt
```

## 失败重试与本地打包

检查或上传失败时，在对应 Actions 运行页面选择 **Re-run failed jobs**。
上传失败的草稿会保留，重试时重新上传同名附件；已经公开发布的 Release 保持原样。
修复源码需要新提交和新版本标签，不移动已发布标签。
若失败发生在校验任务，修复提交后请使用新标签重新发布。

需要本地预览时，在干净且标签指向 HEAD 的源码仓库执行：

```powershell
python tools/build_release.py --tag v0.1.0
```

默认输出到 Git 忽略的 `dist/`，同时生成 `RELEASE_NOTES.md` 供预览。
已有同名产物时会拒绝覆盖，可以用 `--output .verification/release-preview` 选择新的空目录。
相同提交与相同检出文件内容生成一致的 ZIP；ZIP 时间戳固定为源码提交时间。
