# Token 消耗与对话智能评审

评审日期：2026-10-30。源码基线：`f6b414f`，评审开始时工作区干净。

第 1–6 节保留修改前的评审依据；第 7 节记录随后实际落地的范围和验证。

评审覆盖配置生成、人格初始化、主聊天上下文、LivingMemory、知识库、主动聊天、
自主生活、语音／自拍／表情和浏览器调用链；同时只读检查了本机运行配置与数据库汇总。
本报告不包含聊天原文、身份标识、密钥或图片内容。没有调用付费模型、触发 QQ 投递、
重启服务或调整运行配置。以下方案尚未实施，也没有通过真实模型对照实验验证。

## 1. 结论

**目前输出长度合理，输入上下文的使用效率偏低；已有能直接影响记忆连续性的缺陷。
存在同时减少 Token、改善连贯性与自然感的改造空间。**

优先减少重复携带的旧对话、旧图片、无关记忆与工具说明，保护当前话题、明确偏好、
未完成的约定和最近互动。继续缩短回复的收益很小，也可能让聊天变得敷衍。

实际账单未显示在本机数据库中。按当前官方价格重估，已记录的主链用量金额不大，
但它不包含全部插件调用，不能据此认定项目总成本已受控。

## 3. 缺陷与效率问题

### P1：聊天历史按模型容量增长，缺少独立的成本预算

**证据：**运行配置 `compression.max_turns=-1`，采用 `llm_compress`，
兜底上下文容量 128,000；实际容量还可能由模型元数据提高。
安装框架的摘要压缩默认在容量使用率超过 82% 时触发。
当前最大单条统计输入约 6.73 万，尚不足以证明会触发这一容量保护。

**影响：**长会话会持续重发数百轮原文与历史图片。容量没超限，不代表每次闲聊都值得携带这些内容。
旧话题、过期状态和旧图片也增加当前任务选取信息的难度。

**建议：**增加独立于模型容量的聊天输入预算；最近原文与旧话题摘要分层，旧图片转为可追溯的文字摘要，
只有再次指向某张图、需要读字或精确细节时取回原图。保留存档，不删除原聊天或原媒体。
不能只设置 `max_turns` 后直接裁掉旧轮次，那会丢失尚未总结的约定和事实。

**代码入口：**[配置生成](../tools/apply_config.py)；运行依赖中的
`astrbot/core/agent/context/manager.py`、`compressor.py`、`astr_main_agent.py`。
主动聊天直接调用 Provider，也应接入同一预算，不能只修主聊天流水线。

### P1：主动聊天在工具重问时丢失前置钩子补入的记忆

**证据：**`generate_llm_response` 先构造请求，再运行前置钩子；LivingMemory 会向请求的
`extra_user_content_parts` 追加记忆。随后传给 `run_tool_loop` 的却是钩子执行前的
`history_messages`、`final_user_simulation_prompt`、`extra_parts`。
适配器构造请求时还复制了 `extra_parts` 列表，因此钩子追加的内容不在原列表中。

**复现：**以模拟 Provider 和模拟搜索工具执行现有方法。首轮包含钩子追加的记忆标记；
第二次请求中该标记消失，钩子替换的 prompt 和 contexts 也消失。全过程无外部调用。

**影响：**主动消息先检索到用户偏好，再联网搜索时，最终回复可能失去这些偏好。
这既浪费首轮检索与输入，也会表现为“刚刚还记得，转头就忘”。

**建议：**从钩子处理后的实际请求构造唯一的消息序列，后续只追加工具调用与结果。
保留临时片段的“不写入历史”属性，避免为修复丢失而造成长期重复注入。

**代码入口：**[主动聊天 LLM 服务](../overlays/astrbot/data/plugins/astrbot_plugin_proactive_chat/core/services/llm_service.py)，
204–211、351–368
行；[请求适配器](../overlays/astrbot/data/plugins/astrbot_plugin_proactive_chat/core/adapters/astrbot_provider.py)。

### P2：每分钟变化的状态位于 system 中，会阻断后续历史的前缀复用

**证据：**表情转换插件每轮把北京时间、语音状态、自拍记录和媒体规则组成 system 块；
自主生活也把最多约 5,500 字符资料追加到 system。普通主流程先构建人格，再调用这些钩子，
因此稳定人格前缀仍可能复用，但动态 system 后面的长历史无法保持完整前缀一致。

**影响：**相同的历史会在时间或状态变化后重新成为未缓存输入。
这是一条已确认的缓存不利路径；最近两天的命中下降与它相容，但尚未完成因果归因。
DeepSeek
的缓存依赖可匹配的完整前缀，命中也不保证永久保留。[缓存机制](https://api-docs.deepseek.com/guides/kv_cache/)

**建议：**稳定的人格与协议留在 system；当前时间、权限快照、自拍线索、日程和生活资料放在当前轮末尾的
临时上下文中，明确为可信程序状态或普通资料，并保持相应来源边界。
去除人格与每轮媒体规则中的重复表述。不能为缓存而省略本轮真实的权限变化。

**代码入口：**[表情转换插件](../plugins/astrbot_plugin_face_convert/main.py)，990–1019 行；
[自主生活注入](../plugins/astrbot_plugin_life_continuity/main.py)，144–175 行。

### P2：长期记忆与知识库缺少统一的相关性及输入预算

**证据：**LivingMemory 每次自动召回 `top_k=5`，相似度阈值为 0，
最近 72 小时的记忆可占 2 个名额；检索查询默认只有当前消息，近期上下文扩展关闭。
知识库采用自动检索，最终最多 5 个结果。自主生活另有最多约 5,500 字符上下文。

**影响：**“嗯”“那个呢”等短句可能检索不到真正的话题，也可能带入无关的近期记忆。
仅调高相似度阈值也解决不了强制加入近期记忆的问题。多个模块分别有上限，合在一起仍可能过大。

**建议：**维护简短的当前主题与实体线索，改进指代查询；按相关性选择 1–3 条记忆，允许返回零条。
主人偏好和重要未完成约定单独维护，避免依赖每轮向量碰运气。仅在询问用法、指令或特定梗时引入相应知识库，
并用真实正反例校准阈值，而不是直接指定一个未经验证的相似度常数。

**边界：**本地 bge-m3 检索不等于多调用一次付费聊天模型。当前图记忆的原子分类也是规则处理，
不能把图结构存在本身算作额外 LLM 消耗。记忆注入已有临时标记、历史清理和字符上限，这些机制应保留。

**代码入口：**[配置生成](../tools/apply_config.py)，295、306–317 行；
[生活上下文](../plugins/astrbot_plugin_life_continuity/chat.py)，198 行起。
运行依赖中的 LivingMemory `memory_recall.py`、`memory_engine_write_ops.py`、`utils/formatting.py`。

### P2：聊天携带大量用不到的工具，研究步骤又携带完整聊天人格

**证据：**人格初始化设置 `tools=null`，框架据此选择全部已启用插件／MCP 工具，
普通闲聊也可能带上手机连接、管理、日志等 Schema；本地环境另加文件与执行工具。
自主生活的选目标和整理资料请求没有外部工具，但仍拼接完整聊天人格。

**影响：**前者增加每轮固定输入和工具选择负担；后者重复携带语音、自拍、手机操作等与 JSON 研究结果无关的规则。

**建议：**聊天默认保留少量必要工具，其他能力按当前任务、最近任务状态与用户身份启用；
路由本身先用本地规则和现有状态，不为每句话增加一次独立 LLM 分类。
自主研究用短任务协议加必要的兴趣、表达偏好，最终分享时再应用聊天人格。

框架已有 `skills_like` 工具模式，但它在使用工具时可能增加一次参数解析重问。
不建议直接全局切换并假设必然省 Token，应对“少工具完整 Schema”和该模式分别回放比较。
工具按需可见应保留原有执行权限检查。

**代码入口：**[人格初始化](../tools/initialize_api.py)，63–75 行；
[自主研究请求](../plugins/astrbot_plugin_life_continuity/native_agent.py)，60–67 行。

### P2：源码人格更新缺少可核对的升级通道

**证据：**初始化仅在人格不存在时创建，现有人格不会更新；运行人格与源码正文实际不同。

**影响：**修改源码人格后部署，不能据此认定新规则已经生效。旧人格与新补丁的规则也可能产生重复或不一致。
不过现有人格可能包含用户手工调整，差异本身不代表应被强制覆盖。

**建议：**记录导入版本／内容哈希，提供只读差异预览和显式合并更新，保留自定义内容与回退版本；
部署验收显示“源码版本”和“实际使用版本”。

**代码入口：**[初始化脚本](../tools/initialize_api.py)，62–78 行；
[源码人格](../content/persona/大肥鱼-人格.md)。

### P2：总用量统计不完整，调用次数限制也不是 Token 预算

**证据：**主统计写入发生在内部 Agent 流水线结束时。主动聊天、记忆整理、表情情绪分析、
自拍规划、视频理解等直接调用 Provider 的路径不能由该表完整反映。
浏览器内层 Agent 默认 15 步、参数最高 40 步，也不在自主生活每日 20 次调用预算内。
自主生活能记录成功调用的 usage，但超时或响应丢失时无法据此确认供应商是否计费。

**影响：**不能从主面板判断每个功能的总费用，也不能靠“最多调用多少次”控制一次特别大的请求。
主动聊天工具重问还有单独循环，缺少共同的消息、工具结果和 Token 预算。

**建议：**在实际 Provider 调用边界统一记账：调用来源、父轮次、模型、缓存／未缓存输入、输出、耗时、重试、
错误状态。未知用量单独标记，不能当作零。对聊天、研究、浏览器设共享预算，再允许任务显式扩容。
工具结果保留摘要和来源，较长正文按需读取。现有离线回归继续模拟付费 API。

**代码入口：**[主动调用](../overlays/astrbot/data/plugins/astrbot_plugin_proactive_chat/core/services/llm_service.py)；
[浏览器 Agent](../tools/browser_mcp_server.py)，117–141 行；
[生活调用计量](../plugins/astrbot_plugin_life_continuity/native_agent.py)，16–30 行；
[调用次数额度](../plugins/astrbot_plugin_life_continuity/activity_state.py)，225 行起。

## 4. 更少 Token、更多连续性的方案

### 把对话上下文变成分层的有效信息

推荐逐轮构建以下内容，并为每层计量，而不是再添加一篇长提示词：

| 层              | 内容                                          | 普通私聊的初始试验预算 |
|-----------------|-----------------------------------------------|-----------------------:|
| 稳定人格与协议  | 性格、关系边界、表达风格、必要工具协议        |      1,200–1,800 Token |
| 最近原文        | 当前话题的近 8–16 轮，按 Token 和话题长度调整 |            3,000–4,500 |
| 旧话题摘要      | 重要事实、已完成事项、未完成约定、指代线索    |              600–1,000 |
| 相关长期记忆    | 仅选与当前交流相关的事实或经历                |                400–900 |
| 本轮工具 Schema | 当前需要且有权限使用的能力                    |              800–1,500 |
| 当前状态        | 时间、语音权限、少量生活状态                  |                200–400 |

以普通文本闲聊总输入 **8,000–12,000 Token** 为首轮试验目标，图片、读字、长文和设备任务另设预算。
相对目前 33,301 的单条统计输入中位数，数值上存在约 64%–76% 的下降空间；
这只是目标对比， **不是已实现节省率，也不代表费用会同比下降**。缓存命中、摘要成本、
每轮调用次数和任务成功率都必须一起测量。

旧消息跨越预算或话题结束时才增量总结，不为每条问候调用总结模型。
窗口在一个话题段内保持稳定，避免每轮移动窗口导致长前缀不断变化。
事实与原图留在本地，需要精确回忆时再按来源取回。

### 用简短、持久的关系与事项状态改善“活人感”

建议保存少量有来源的状态：当前话题、用户明确反馈、已完成事项、未完成约定、
最近共同经历、下一次适合提起的事情。区分用户事实、角色日常、推测和工具确认结果。
“用户说吃过饭”应关闭该轮吃饭提醒；“不方便听”应直接影响表达方式；
“上次不喜欢恐怖题材”应影响下次推荐。它们比重发几百轮对话更直接地支持连续性。

角色可以有偏好、自己的意见和连贯日常，不需要每轮撒娇、追问、加表情或主动刷存在感。
当前人格已经包含不少正确方向，优先让程序稳定提供必要状态并落实这些规则。

### 主动互动依据事件和话题，减少空转

保留免打扰、未回复上限和共享发送门控。对“有了新进展”“约定时间到了”“上次关心的事情需要跟进”
等事件生成一次自然消息；没有值得说的内容时允许不生成、不发送。
事件候选和冷却判断先本地完成，避免每隔几分钟让模型判断一次要不要说话。

当前自主生活是主人触发的一次有限研究，没有周期性自主生活调度；
`share_enabled=false` 也意味着研究后不会自动分享。不能把它描述成已完成的全天自主生活系统。
下一步应从有依据的进展与话题衔接做起，保留现有次数、暂停和去重机制。

### 把推理能力用在真正困难的请求上

目前聊天模型统一关闭 thinking，适合节省普通聊天的输出与延迟。
可在复杂排错、规划、矛盾核对时，选择一个输入更短、预算明确的推理路径，
得到结论和证据后自然回复；不为普通闲聊固定增加“计划一次、反思一次、回复一次”。

DeepSeek 当前支持按请求开启思考并控制 effort；携带 tools 时对历史 reasoning 内容还有协议要求，
现有主动聊天重问逻辑不能直接假设兼容。应先修复消息序列、做兼容回归，再小范围比较。
推理模式增加的费用应由普通请求节省的预算承担。[官方思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode/)

## 5. 实施顺序与验收

| 顺序 | 工作                                            | 验收重点                                                 |
|------|-------------------------------------------------|----------------------------------------------------------|
| 1    | 修复主动聊天重问丢记忆；补调用来源与 usage 记录 | 搜索前后偏好与临时上下文不丢失；不重复保存；未知费用可见 |

## 7. 首轮落地（2026-10-30）

本轮先修复确定的连续性缺陷，并建立保留原文的上下文工作区与实际请求计量：

- **主动聊天工具重问**从钩子处理后的实际 `ProviderRequest` 组装消息，保留追加记忆、媒体、
  prompt／contexts 修改、模型选择和已有工具结果。临时资料不会因此写入历史；工具结果限制长度，
  超过工具轮数时不发送未完成的回答。
- **动态状态后置**：语音权限、当前时间、自拍记录、日程和自主生活资料采用本轮临时内容。
  稳定协议继续放在 system，更新本轮状态不会重写其他插件的内容，也不会留下旧日程。
- **出站上下文工作区**：在 DeepSeek 的 Provider 请求边界整理较早对话，原始请求、Runner 消息和聊天存档保持完整。
  每次最多推进一次增量摘要；按完整对话轮次处理，工具调用与结果保持成组。
  摘要尚未覆盖全部旧记录时继续携带完整历史；摘要错误后冷却五分钟，期间不重复调用摘要模型。
  摘要不把图片 Base64 当成文字，明确追问历史图片时仍可带上最近一张原图。
- **保守的工具筛选**：仅对“你好”“晚安”等明确社交短句缩小工具集。
  “好”“嗯”、有未结束工具调用、图片及任务消息保留原能力，避免把确认或指代误判成闲聊。
  自主生活的私有 JSON 研究改用简短任务身份，不再重复携带整篇聊天媒体规则。
- **模型计量**：主聊天、主动聊天、记忆整理、表情分析及媒体理解中经过 OpenAI 兼容聊天适配器的实际 SDK 尝试，
  与浏览器内层调用写入同一运行目录 SQLite 表。包含输入总量、已知缓存／未缓存量、输出、来源、耗时、
  错误类型和流式中断；不记录原始聊天、工具参数、密钥或身份。
  浏览器关闭 SDK 隐藏重试，保留 Agent 的有限失败处理。TTS、生图和其他未接入适配器不算入该表。
- **人格同步**：新增显式的预览／同步入口，先备份、只更新“大肥鱼”正文，并读回核对。
  本机运行正文已与最新源码一致；工具、技能、开场和其他人格保持原配置。

### 配置与管理

DeepSeek Provider 的 `companion_context` 初始配置如下。安装和部署会补齐缺失配置；已有自定义值保留。

```json
{
  "enabled": true,
  "input_budget": 16000,
  "recent_rounds": 12,
  "summary_max_tokens": 900,
  "summary_input_chars": 24000,
  "route_simple_chat_tools": true
}
```

`input_budget` 是估算输入的摘要触发线，**不是每次请求的硬上限或每日花费上限**。
保留最近至少 12 轮原文，并以四轮为一批移动旧记录边界；工具说明和当前大附件仍可能使输入超过触发线。
首次为既有长会话补齐摘要会增加少量调用，此后复用摘要并增量更新。
摘要输入按最多 24,000 字符的完整轮次分批，输出上限 900 Token 在实际 SDK 负载中设置；
失败或单轮资料过大时保留完整历史，不静默裁掉未处理内容。模型推理模式维持原配置。

在源码根目录使用：

```powershell
python tools/launch.py chat-usage --days 7
python tools/launch.py sync-persona
python tools/launch.py sync-persona --apply
```

前两条分别只读统计和预览人格差异；最后一条备份后同步正文。
用量表位于运行目录 `astrbot/data/plugin_data/dafeiyu_context/context.db`，
人格备份位于运行目录 `backups/personas/`，均不纳入 Git。
