# 3～5 分钟视频识别

插件 v1.2.0 的默认目标是理解 3～5 分钟视频的大致内容。它先下载视频，再把画面描述和
语音转写按时间送给原来的聊天模型；不用换聊天模型，也不用额外添加一次总结 API 调用。

## 默认处理方式

| 项目 | 行为 |
|---|---|
| 视频范围 | 最多前 300 秒；更长的视频会明确注明后续未处理 |
| 画面 | 全范围均匀取最多 16 帧，包含开头和接近结尾；每 4 帧带时间戳共同理解 |
| 音频 | 每 60 秒一段，转为 16 kHz 单声道 WAV，逐段转写并保留时间范围 |
| 文件大小 | 下载与 NapCat 本地共享文件均限 80 MiB；视频下载流式写入磁盘 |
| 并发 | 默认同时处理 1 条媒体；视频内部最多 2 个工作任务 |
| 等待 | 等待媒体空位最多 10 秒；获取空位后，整个视频处理最多 300 秒 |
| 失败 | 一段失败仍继续其他段；总超时返回已完成内容；取消请求、回收 ffmpeg 后清理临时文件 |

16 帧覆盖的是整个时间范围，**不等于逐帧看完整片**。快速动作、短暂字幕、只出现一瞬的
物体可能遗漏。音频在切段边界也可能漏词；时间戳是片段范围，不是逐字对齐结果。
默认 5 分钟视频通常最多产生 4 次视觉请求和 5 次 ASR 请求，比原来短片配置消耗更多模型用量。
300 秒是处理等待上限，不是保证的响应速度，也不保证网络异常时所有片段都能完成。

## 安装与升级

把仓库中的 `plugin/astrbot_plugin_face_convert/main.py` 和 `metadata.yaml` 更新到
AstrBot 实际运行的 `data/plugins/astrbot_plugin_face_convert/`，保留原有 `face_map.json`。
Docker 部署按宿主机挂载的 `astrbot/data/plugins/astrbot_plugin_face_convert/` 更新。

首次安装无需添加配置，默认即为上述方案。已有 `config.json` **不会被自动改写**；
如果仍写着 `max_media_mb: 20` 或 `video_timeout_s: 150`，这些旧值仍然生效。
请把下面的媒体参数合并到原配置，保留自己设置的其他选项：

```json
{
  "max_media_mb": 80,
  "video_max_duration_s": 300,
  "video_max_frames": 16,
  "video_audio_chunk_s": 60,
  "video_timeout_s": 300,
  "vl_timeout_s": 60,
  "asr_timeout_s": 60,
  "max_concurrent_media": 1,
  "video_workers": 2,
  "media_queue_timeout_s": 10
}
```

保存后重载插件或重启 AstrBot。只修改仓库、没有更新运行目录或重载，不会改变线上行为。
配置中的视频时长限制为 1～300 秒，帧数为 1～32，音频分段为 10～60 秒，内部工作任务为 1～2；
输入越界会被限制到允许范围。提高帧数会增加识别成本和超时概率。

仍沿用 AstrBot 配置中 `id=dashscope_tts` 的 API key，以及已安装 DashScope SDK 的
`base_http_api_url`。未安装 SDK 时使用北京区域的默认接口；密钥必须与接口区域匹配。
请求使用已有的 `aiohttp` 依赖和 Base64 媒体，不需要额外安装 ffprobe。

## 验证

```bash
python tests/test_face_rules.py
python tests/test_video_processing.py
```

第二组测试需要 `aiohttp` 和 `ffmpeg`。它生成 3、5、5.5 分钟的真实测试视频，检查结尾
画面与音轨是否处理，并覆盖静音短片、下载限额、部分失败、取消清理和本地 HTTP 请求。
模型响应使用测试替身，**没有调用付费模型或连接 QQ**。合并部署后仍需用真实 QQ 视频确认
NapCat 文件解析、API key/区域、模型可用性和理解效果。

接口格式参考：[百炼视觉理解](https://www.alibabacloud.com/help/en/model-studio/vision)、
[Qwen-ASR API](https://www.alibabacloud.com/help/en/model-studio/qwen-asr-api-reference)。
